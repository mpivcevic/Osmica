## Problem Statement

Small café and hospitality teams in Croatia (and the broader ex-YU market) coordinate
shift swaps and days off through WhatsApp group chats or verbal requests to the owner.
There is no tool in Croatian, no tool that fits a 3-8 person team without a subscription,
and no tool that works the way these teams actually work (mobile-first, WhatsApp-native,
owner as single coordinator). The existing software market (7shifts, Homebase, Deputy)
is English-first, feature-heavy, and designed for larger teams.

## Phase A Implementation Spec

**localStorage data schema:**
```json
{
  "zm_state": {
    "owner": { "name": "", "pin": "", "phone": "", "businessName": "", "appUrl": "" },
    "waiters": [ { "id": "", "name": "", "pin": "", "phone": "", "pattern": {}, "vacations": [], "color": "" } ],
    "requests": [ { "id": "", "waiterId": "", "date": "", "shift": "", "note": "", "status": "", "coveredBy": null, "approvedBy": null, "createdAt": "" } ],
    "dateSchedule": {},
    "theme": "light"
  }
}
```
On app load: read `localStorage.getItem('zm_state')`, merge into STATE.
On every STATE mutation: `localStorage.setItem('zm_state', JSON.stringify(STATE))`.
Data survives refresh and browser close. Not shared across devices (by design for Phase A).

**PWA manifest requirements:**
- `manifest.json` with `name`, `short_name`, `start_url`, `display: standalone`, `background_color`, `theme_color`
- Icons at minimum 192x192 and 512x512 PNG — must be created if they don't exist
- `<link rel="manifest" href="manifest.json">` in `<head>`

**Service worker (minimal):**
- Cache-first for the single HTML file and manifest
- Offline behavior: app loads from cache, shows toast "Offline — neke funkcije nisu dostupne" if network needed
- Register via `navigator.serviceWorker.register('/sw.js')` on DOMContentLoaded

**Deployment:**
- GitHub Pages or Netlify (free static hosting)
- HTTPS required for PWA install prompt — both platforms provide this

**Estimate caveat:** 1-2 days assumes the existing STATE management is centralized (it is — single `STATE` object). If scattered across DOM, add 1-2 days for refactoring before localStorage can be layered on.

## Demand Evidence

- A specific café owner (friend of the builder) asked for a scheduling tool — initially
  framed as "an Excel sheet." He's not PC-savvy; a mobile-first solution fits him better
  than a spreadsheet.
- Owner has not seen the app yet. Demand is confirmed for the problem, not yet for
  this specific solution.
- No waiter adoption data exists. The builder acknowledges this is the primary risk.

## Status Quo

The café currently uses nothing structured — owner coordinates all swaps verbally or
via direct WhatsApp messages. No schedule record exists. Swaps are ad hoc.

## Target User & Narrowest Wedge

**Owner (primary decision-maker):** Croatian café owner, not PC-savvy, runs a team of
3-8 people. Currently coordinates everything manually. Would benefit from a single view
of who's working when, and a way for team members to request swaps without calling him.

**Waiter (daily user):** Croatian hospitality worker, mobile-only, already lives in
WhatsApp. Will not bookmark a URL or remember a PIN unless there's a reason to.
A home screen icon (PWA) changes this equation significantly.

**Narrowest wedge:** One café, one owner, the builder's friend. Get the team to use
it for 2 weeks. Observe what they actually do.

## Constraints

- Current architecture: single-file HTML, in-memory only, no backend, no persistence
- No user accounts — data does not survive a page refresh or new device
- No push notifications — relies on WhatsApp links for outbound communication
- Croatian UI only — this is a feature, not a limitation, for the target market
- Builder is a solo developer; backend rebuild is a significant investment

## Premises

1. The owner will prefer the mobile app over an Excel sheet — hypothesis, to be
   confirmed when shown the app. He is not PC-savvy; mobile-first is the right
   direction. But he asked for Excel and has not seen the app yet.
2. Waiter adoption is uncertain — the builder does not know if waiters will use it.
   URL friction is the identified blocker. PWA install partially solves this.
3. The current single-file architecture cannot support a startup — confirmed. User
   accounts, persistent data, and multi-tenant support all require a backend rebuild.
4. The Croatian/regional market is the real wedge — confirmed. English-first tools
   have poor cultural and language fit for small hospitality teams in this market.
   No one has built the WhatsApp-native, Croatian-first version of this product.

## Approaches Considered

### Approach A: Validate First (localStorage + PWA install, deploy now)
- Add localStorage so data persists between sessions on the same device
- Add a PWA manifest + service worker so the owner can install it to his home screen
- Deploy to GitHub Pages or Netlify (free, instant)
- Hand it to the friend this week. Watch for 2 weeks.
- **Effort:** S (1-2 days) | **Risk:** Low

### Approach B: Build the Real Product (backend + auth + PWA push)
- Supabase (free tier): auth, PostgreSQL database, real-time
- Proper multi-tenant: each café is an isolated account
- PWA with Web Push API — notifications without WhatsApp dependency
- Mobile-installable, subscription-ready
- **Effort:** XL (2-4 months solo) | **Risk:** High before validation

### Approach C: WhatsApp Bot as Waiter UI
- Keep owner admin panel as-is
- Waiters interact via WhatsApp bot (Meta Business API)
- No URL, no PIN, zero behavior change for team members
- **Effort:** L (4-6 weeks + Meta API approval) | **Risk:** Medium

## Recommended Approach

**A then B.** Ship what exists (with localStorage + PWA) to the friend's café this week.
Measure whether the waiters actually use it. If yes — that is the only proof needed to
justify rebuilding with a backend. If no — find out why (URL friction? PIN confusion?
just texting the owner anyway?) and fix it before spending months on infrastructure.

The Approach C (WhatsApp bot) remains the most radical differentiator and should be
revisited after validation. If waiters won't use the web app, a WhatsApp bot becomes
the obvious answer — and it's genuinely defensible against English-first competition
because the WhatsApp-native UX is culturally specific.

## Open Questions

1. Will the owner accept the app instead of the Excel sheet he asked for? He has not
   seen it yet — showing him is The Assignment.
2. Will any waiter open the app without being directly asked to by the owner?
3. What does the owner consider "it's working" — fewer direct calls from waiters?
   Visible schedule? Peace of mind?
4. Is there a second café owner (beyond the friend) who would try this immediately?
   A second customer confirms the market. One customer confirms a friendship.
5. The app uses 4-digit PINs for login. Will team members remember their PIN, or
   will they ask the owner every time? (If yes, this is the first thing to fix.)

## Success Criteria

Phase A (no accounts — measure behavior, not identity):
- Owner opens the app and builds at least one real schedule (not dummy data)
- At least one team member opens the app on their own device (confirmed by asking)
- At least one swap request is submitted and resolved through the app, not via WhatsApp
- Owner says unprompted: "the team is using it" or "it's easier than WhatsApp"

Phase B (with accounts — measure engagement):
- At least half the team opens the app at least once per week without being reminded

## Distribution Plan

**Phase A (validation):**
- GitHub Pages or Netlify free static hosting
- Owner installs PWA to home screen; shares link to team via WhatsApp
- No custom domain needed yet

**Phase B (startup):**
- Custom domain, proper auth, subscription billing per café location
- Details deferred until Phase A validation data exists

## Dependencies

- Phase A: localStorage implementation (~2 hours), PWA manifest (~1 hour), deploy (~1 hour)
- Phase B: Supabase project setup, auth flow, database schema, migration from in-memory model
- Phase B blocks on Phase A validation data
