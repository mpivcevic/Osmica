### What Stage C actually does

Waiters get a real Supabase identity, bound to their device, instead of proving
themselves with a 4-digit PIN that the server checks. That kills the
"guess a PIN and discover who you became" surface, and — more importantly — gives
waiters an `auth.uid()`, without which **Stage D's RLS policies cannot be
written at all.**

It runs in four steps, additive first, destructive last:

- **C1** — add the column and the linking function *(migration written)*
- **C2** — waiters start signing in, nothing else changes *(v4.37 written)*
- **C3** — the PIN becomes a local device unlock *(not started)*
- **C4** — delete `login_waiter_by_pin`, `verify_waiter_pin`, `pin_attempts`, `pin_hash` *(not started)*

Today is C1 and C2. C3 must not start until every waiter is linked.

### The one thing I want you to read before starting

`init()` routed **any** Supabase session into the owner's admin panel. After C2 a
waiter *has* a session — an anonymous one. Without a guard, every linked waiter
would land in the owner's view, with the owner's column grants, on their next app
open.

The guard (`!session.user.is_anonymous`) ships inside v4.37 and is not
deferrable. **Step 5 below is the test that proves it.** If that test fails,
stop everything else.

## What step 1 opened — found 19 Aug

A Supabase linter mail (`rls_disabled_in_public`, "Table publicly accessible")
prompted a check of what the `authenticated` role actually holds:

| table | anon | authenticated |
|---|---|---|
| cafes | SELECT | DELETE, INSERT, SELECT, UPDATE |
| date_schedules | SELECT | DELETE, INSERT, SELECT, UPDATE |
| shift_requests | SELECT | DELETE, INSERT, SELECT, UPDATE |
| waiters | column-restricted SELECT | DELETE, INSERT, SELECT, UPDATE |

Every migration to date narrowed `anon` and deliberately left `authenticated`
alone — `006` says so in a comment: *"Unchanged: the owner reads phone and
invite_token for their own café."* That was sound while the owner's password was
the only way to obtain the role.

Step 1 made the role self-service. Anyone holding the publishable key — public
by design, `osmica.html:1114` — could mint an `authenticated` session and inherit
every grant written for the owner, on every café. With RLS off, grants were the
only gate.

**Mitigation, already applied:** anonymous sign-ins switched **off on
production** 19 Aug. Production runs v4.36, which never calls
`signInAnonymously()`, so this costs nothing. **Dev stays enabled** — it holds
seed data, and step 5 needs it.

### Why a grant fix alone cannot work

The owner is *also* `authenticated` and genuinely needs that CRUD for the admin
panel. Grants are per-role, so no `GRANT`/`REVOKE` combination separates the
owner from an anonymous waiter. Two mechanisms are required:

- **rows** → RLS policies keyed on the `is_anonymous` JWT claim
- **columns** → grants, because RLS filters rows and *cannot hide a column*.
  Any session that can read a waiter row reads `pin_hash` too, policy or not.

That is `supabase/migrations/015_scope_authenticated_role.sql` — written 19 Aug,
**not applied anywhere**. It needs a client change (v4.38): revoking `phone` and
`invite_token` from the role breaks the owner's two `WAITER_COLS_ADMIN` reads at
`osmica.html:1332` and `:2145`, which must move to the new
`owner_list_waiters()` RPC.

### Consequence for Stage C

**C cannot reach production ahead of D.** Enabling anonymous sign-ins on
production *is* the exposure until 015 lands. Stage C testing continues on dev,
where it is unaffected.

### Open question — waiter writes may already be broken

## Three decisions I need from you before C3

Detail and my reasoning are in `osmica_stage_c_plan.md`. Short versions:

**1. One device per waiter?** An anonymous session lives in one browser, so phone
*and* tablet means two invites and two identities — which the `UNIQUE` constraint
currently forbids. *My recommendation: accept one device; add more when someone
actually asks.*

**2. Recovery when a waiter clears their browser data.** After C3 there's no
self-service path — the owner reissues an invite. The alternative is a
server-side recovery check, which reintroduces exactly the oracle C4 deletes.
*My recommendation: owner reissues.*

**3. The dev identity switcher gets worse.** Becoming a waiter will mean holding
their session, and one browser holds one identity. Either test with separate
private windows, or keep the PIN path alive on dev only. *My recommendation:
private windows — a second permanent divergence is how dev stops being a faithful
test of production.*
