### What Stage C actually does

Waiters get a real Supabase identity, bound to their device, instead of proving
themselves with a 4-digit PIN that the server checks. That kills the
"guess a PIN and discover who you became" surface, and — more importantly — gives
waiters an `auth.uid()`, without which **Stage D's RLS policies cannot be
written at all.**

It runs in four steps, additive first, destructive last:

- **C1** — add the column and the linking function *(migration written)*
- **C2** — waiters start signing in, nothing else changes *(v4.37 written)*
- **C3** — the PIN becomes a local device unlock *(not started)*
- **C4** — delete `login_waiter_by_pin`, `verify_waiter_pin`, `pin_attempts`, `pin_hash` *(not started)*

Today is C1 and C2. C3 must not start until every waiter is linked.

### The one thing I want you to read before starting

`init()` routed **any** Supabase session into the owner's admin panel. After C2 a
waiter *has* a session — an anonymous one. Without a guard, every linked waiter
would land in the owner's view, with the owner's column grants, on their next app
open.

The guard (`!session.user.is_anonymous`) ships inside v4.37 and is not
deferrable. **Step 5 below is the test that proves it.** If that test fails,
stop everything else.

## Three decisions I need from you before C3

Detail and my reasoning are in `osmica_stage_c_plan.md`. Short versions:

**1. One device per waiter?** An anonymous session lives in one browser, so phone
*and* tablet means two invites and two identities — which the `UNIQUE` constraint
currently forbids. *My recommendation: accept one device; add more when someone
actually asks.*

**2. Recovery when a waiter clears their browser data.** After C3 there's no
self-service path — the owner reissues an invite. The alternative is a
server-side recovery check, which reintroduces exactly the oracle C4 deletes.
*My recommendation: owner reissues.*

**3. The dev identity switcher gets worse.** Becoming a waiter will mean holding
their session, and one browser holds one identity. Either test with separate
private windows, or keep the PIN path alive on dev only. *My recommendation:
private windows — a second permanent divergence is how dev stops being a faithful
test of production.*

## Where this leaves things

Stage C is only half the fix. It creates identities; **Stage D writes the
policies that use them.** Anonymous reads of names, colours, shift patterns and
schedules stay open until D lands, so C is only worth doing as the first half of
a pair.

After C and D, someone who reads the entire source, extracts the publishable key
and pokes at the API can enumerate nothing, read nothing and write nothing.
