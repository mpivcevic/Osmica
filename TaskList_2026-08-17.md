### What Stage C actually does

Waiters get a real Supabase identity, bound to their device, instead of proving
themselves with a 4-digit PIN that the server checks. That kills the
"guess a PIN and discover who you became" surface, and — more importantly — gives
waiters an `auth.uid()`, without which **Stage D's RLS policies cannot be
written at all.**

It runs in four steps, additive first, destructive last:

- **C1** — add the column and the linking function *(migration written)*
- **C2** — waiters start signing in, nothing else changes *(v4.37 written)*
- **C3** — the PIN becomes a local device unlock *(not started)*
- **C4** — delete `login_waiter_by_pin`, `verify_waiter_pin`, `pin_attempts`, `pin_hash` *(not started)*

Today is C1 and C2. C3 must not start until every waiter is linked.

### The one thing I want you to read before starting

`init()` routed **any** Supabase session into the owner's admin panel. After C2 a
waiter *has* a session — an anonymous one. Without a guard, every linked waiter
would land in the owner's view, with the owner's column grants, on their next app
open.

The guard (`!session.user.is_anonymous`) ships inside v4.37 and is not
deferrable. **Step 5 below is the test that proves it.** If that test fails,
stop everything else.

## What step 1 opened — found 19 Aug

A Supabase linter mail (`rls_disabled_in_public`, "Table publicly accessible")
prompted a check of what the `authenticated` role actually holds:

| table | anon | authenticated |
|---|---|---|
| cafes | SELECT | DELETE, INSERT, SELECT, UPDATE |
| date_schedules | SELECT | DELETE, INSERT, SELECT, UPDATE |
| shift_requests | SELECT | DELETE, INSERT, SELECT, UPDATE |
| waiters | column-restricted SELECT | DELETE, INSERT, SELECT, UPDATE |

Every migration to date narrowed `anon` and deliberately left `authenticated`
alone — `006` says so in a comment: *"Unchanged: the owner reads phone and
invite_token for their own café."* That was sound while the owner's password was
the only way to obtain the role.

Step 1 made the role self-service. Anyone holding the publishable key — public
by design, `osmica.html:1114` — could mint an `authenticated` session and inherit
every grant written for the owner, on every café. With RLS off, grants were the
only gate.

**Mitigation, already applied:** anonymous sign-ins switched **off on
production** 19 Aug. Production runs v4.36, which never calls
`signInAnonymously()`, so this costs nothing. **Dev stays enabled** — it holds
seed data, and step 5 needs it.

> ✅ **Superseded 19 Aug.** That mitigation was a stopgap and has been undone on
> purpose. `015` is applied to production, so the role no longer carries the
> grants that made the switch dangerous, and 9d turned anonymous sign-ins back
> on. The escalation below is closed; the section stays because trap 6 is worth
> re-reading before the next auth change.

### Why a grant fix alone cannot work

The owner is *also* `authenticated` and genuinely needs that CRUD for the admin
panel. Grants are per-role, so no `GRANT`/`REVOKE` combination separates the
owner from an anonymous waiter. Two mechanisms are required:

- **rows** → RLS policies keyed on the `is_anonymous` JWT claim
- **columns** → grants, because RLS filters rows and *cannot hide a column*.
  Any session that can read a waiter row reads `pin_hash` too, policy or not.

That is `supabase/migrations/015_scope_authenticated_role.sql` — written 19 Aug,
**and applied to dev (step 8) and production (step 9b) on 19 Aug**. It needs a client change (v4.38): revoking `phone` and
`invite_token` from the role breaks the owner's two `WAITER_COLS_ADMIN` reads at
`osmica.html:1332` and `:2145`, which must move to the new
`owner_list_waiters()` RPC.

### Consequence for Stage C

**C cannot reach production ahead of D.** Enabling anonymous sign-ins on
production *is* the exposure until 015 lands. Stage C testing continues on dev,
where it is unaffected.

## Three decisions — ✅ ALL DECIDED 22 Aug

Detail and the original reasoning are in `osmica_stage_c_plan.md`.

**1. One device per waiter? — ✅ YES, accept one device.** An anonymous session
lives in one browser, so phone *and* tablet would mean two invites and two
identities, which `014`'s `UNIQUE` constraint on `auth_user_id` forbids. More
devices get added if somebody actually asks, not in advance.

**2. Recovery when a waiter clears their browser data — ✅ OWNER REISSUES,
⚠️ NOT IMPLEMENTED.** No self-service path. The alternative, a server-side
recovery check, reintroduces exactly the PIN oracle C4 exists to delete, and it
is not worth trading a closed hole for a convenience nobody has asked for yet.

> 🔴 **The decision is right; the client cannot carry it out.** Found 22 Aug
> while diagnosing 7c-3.
>
> - **The 💬 button does not reissue.** `osmica.html:2866` builds a URL from the
>   waiter's *existing* `invite_token`. Nothing in the client rotates a token on
>   demand — only a successful link rotates it, at `014:89`.
> - **An already-linked row cannot be relinked.** `link_waiter_to_auth`'s claim
>   query requires `auth_user_id IS NULL` (`014:71`). A waiter whose row is
>   already bound, arriving from a new browser, falls through to
>   **`invalid_token`** — not `already_linked`, which is returned only when the
>   *caller's* uid is already bound (`014:57-63`).
> - **The client swallows it.** Only `ok` and `already_linked` count as success
>   (`osmica.html:1619`); `invalid_token` logs a console warning and returns
>   false. The waiter still gets in by PIN and is read-only, with nothing on
>   screen to say so.
>
> So recovery today means a manual `update public.waiters set auth_user_id =
> null where …` before the invite will take. **C3 work item:** an owner-facing
> unlink-and-reissue that clears `auth_user_id` and rotates the token in one
> action.

**3. The dev identity switcher — ✅ PRIVATE WINDOWS FOR UI, SCRIPTED SESSIONS
FOR POLICY.** The PIN-path-on-dev-only option is rejected: this whole session was
spent removing a dev divergence that had quietly falsified `015`'s results for
eighteen days, and adding a fresh permanent one immediately afterwards is the
wrong lesson.

> **22 Aug — a third option appeared, and it is better than either original.**
> An anonymous session can be minted straight from the API:
>
> ```bash
> JWT=$(curl -s -X POST "$URL/auth/v1/signup" -H "apikey: $KEY" \
>   -H "Content-Type: application/json" -d '{}' \
>   | python3 -c 'import sys,json;print(json.load(sys.stdin)["access_token"])')
> curl -s "$URL/rest/v1/waiters?select=phone" -H "apikey: $KEY" -H "Authorization: Bearer $JWT"
> ```
>
> That gives as many simultaneous identities as wanted, with no browser profiles
> involved, and it tests the policies directly instead of through the UI. It is
> how 7c-2 and 7c-5 were verified. It does not replace a browser for anything
> visual — but for "can this identity write", it is faster and more trustworthy.
>
> Each call leaves an anonymous row in `auth.users`. Harmless — a real waiter
> completing an invite creates exactly the same kind of row — but they can be
> deleted under Authentication → Users to keep the list readable.
